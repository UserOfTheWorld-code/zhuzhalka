# Подпись Жужалки с версии 0.2

APK для пользователей собираются в варианте `release` и подписываются одним постоянным приватным ключом. Публичный SHA-256 сертификата записан в [`scripts/release-signing-cert.sha256`](../scripts/release-signing-cert.sha256). Gradle проверяет этот отпечаток до сборки release, а упаковщик повторно проверяет подпись и манифест каждого APK. Приватный ключ и пароль никогда не входят в репозиторий, исходный ZIP или артефакты CI.

Версия 0.3.0-alpha.4 использует `versionCode = 5000303` для всех ABI и обеих дистрибуций. Каждый следующий опубликованный APK должен иметь больший код. Не возвращайте ABI-зависимые коды: universal и arm64 должны обновлять друг друга. У F-Droid отдельный package ID с суффиксом `.fdroid`.

## Однократный переход с 0.1

Публичная 0.1 была подписана временным debug-ключом GitHub Actions, который не сохранился. Новый сертификат не может заменить его при обновлении. Экспортируйте профили и ссылки подписок, удалите 0.1, установите новый выпуск с постоянной подписью и импортируйте данные. После этого версии с постоянной подписью устанавливаются поверх приложения. Не удаляйте 0.1 до сохранения нужных настроек.

## Локальная сборка в Windows

Ключ `release.jks`, зашифрованный Windows DPAPI пароль `password.dpapi` и публичный сертификат `release-certificate.der` хранятся вне репозитория в `%LOCALAPPDATA%\Zhuzhalka\signing`. Доступ к папке ограничен текущей учётной записью Windows. DPAPI-файл расшифровывается этой же учётной записью; его копия сама по себе не является переносимой резервной копией пароля.

После установки JDK 21, Android SDK и подготовки нативных библиотек:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/build-signed-release.ps1
```

Скрипт читает защищённый пароль только в процессе сборки, передаёт его Gradle через окружение, не печатает его и запускает Gradle без постоянного daemon. Он не создаёт новый ключ автоматически. APK находятся в `V2rayNG/app/build/outputs/apk/playstore/release/` и `fdroid/release/`.

Проверка конфигурации без полной сборки:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/build-signed-release.ps1 -Tasks :app:verifyReleaseSigning
```

Сохраните приватный ключ и пароль в защищённой независимой резервной копии. Потеря этого ключа лишает возможности выпускать совместимые обновления. Не отправляйте их в чат, публичные файлы или Git. При переносе на другой компьютер восстановите прежний ключ и заново защитите его пароль DPAPI под нужной учётной записью.

## GitHub Actions

Основной workflow **Publish verified local APKs** публикует уже собранные и подписанные
локально файлы. Приватный ключ и пароль не передаются в GitHub; Actions Secrets для этого
варианта не нужны. Публикация разрешена только при ручном запуске с `master` в
`UserOfTheWorld-code/zhuzhalka`, вход — один `bundle_commit` (40 строчных hex-символов).

Сначала завершите локальные проверки, сохраните финальные исходники в `master` и выполните
`python scripts/package-release.py --output release-dist` из чистого checkout с подготовленными
JDK/Android SDK. Упаковщик принимает только release APK с правильными пакетом, версией,
кодом, постоянным сертификатом и выключенным `debuggable`.

Для передачи готовых публичных файлов создаётся отдельный Git tree на основе дерева
коммита исходников. В него добавляются `manifest.json` и каталог `chunks/`; существующие
файлы проекта сохраняются без изменений. Поля манифеста:

- `schema: 1`, `version: "0.3.0-alpha.4"`, `version_code: 5000303`;
- `source_commit`: полный SHA исходников; он должен совпасть с `GITHUB_SHA` запуска и
  `source_commit` внутри `BUILD_INFO.json` исходного ZIP;
- `signing_certificate_sha256`: значение из `scripts/release-signing-cert.sha256`;
- `assets`: ровно четыре записи в порядке `Zhuzhalka_0.3.0-alpha.4_arm64-v8a.apk`,
  `Zhuzhalka_0.3.0-alpha.4_universal.apk`, `Zhuzhalka_0.3.0-alpha.4_sources.zip`, `SHA256SUMS`.

У каждой записи `assets` поля `name`, `size` (байты), `sha256` и `chunks`.
У каждой части поля `name`, `size`, `sha256`; имена строго `chunks/00-0000.bin`,
`chunks/00-0001.bin` и далее: первые две цифры — индекс файла `00`–`03`, последние четыре —
индекс части с нуля. Части идут по порядку, каждая 4 МиБ, кроме последней части файла.
SHA-256 записывается строчными hex-символами. Пределы: 256 МиБ на APK, 128 МиБ на исходный
ZIP, 64 КиБ на `SHA256SUMS`; последний содержит ровно три суммы APK/ZIP с двумя пробелами
между хешем и именем. Никаких приватных ключей, паролей или пользовательских конфигураций
в tree не добавляют.

После создания bundle-коммита создайте ветку `release-bundle/alpha4-<bundle_commit>` на его SHA.
Подготовьте draft релиза `v0.3.0-alpha.4` и запустите **Actions → Publish verified local APKs →
Run workflow** на `master`, передав этот SHA в `bundle_commit`.

`fetch-release-bundle.py` получает данные только с фиксированного GitHub-репозитория и коммита,
сверяет все размеры/хеши, затем проверяет APK через `apksigner`/`aapt2` и происхождение исходного
архива. Ошибка не оставляет частично подготовленный каталог выпуска. Workflow использует JDK 21
и Android Build Tools 37.0.0; новые лицензии SDK автоматически не принимаются.

`publish-release.sh` использует автоматический `GITHUB_TOKEN`, проверяет draft и соответствие
тега исходному коммиту, загружает четыре файла и скачивает их обратно для побайтовой сверки.
Затем публикует prerelease с `--latest=false`. Только после успеха workflow удаляет временную
ветку bundle, предварительно проверив её точный SHA. При ошибке ветка остаётся для повторения
операции. Уже публичный выпуск не перезаписывается.

Это публикация локальных артефактов: облачный запуск не повторяет сборку, модульные тесты
или Android QA. Наличие инструкции не означает, что alpha.4 уже опубликована.

### Дополнительный вариант: сборка и подпись в облаке

**Build Android APKs** с ручным входом `publish_release=true` на `master` собирает APK заново,
подписывает и публикует их в предварительно созданный draft `v0.3.0-alpha.4`.
Обычные push/PR собирают debug APK без доступа к ключу. Отсутствие постоянного ключа
в режиме публикации приводит к ошибке, а не к замене его debug-подписью.

Только для этого дополнительного варианта, после отдельного разрешения владельца передать
ключ в GitHub, настраивают два Actions Secrets:

- `ZHUZHALKA_KEYSTORE_BASE64`: Base64 от существующего `release.jks`.
- `ZHUZHALKA_KEYSTORE_PASSWORD`: его пароль; тот же пароль используется для alias `zhuzhalka-release`.

Base64 — кодировка, не шифрование; её значение также является секретом. Данные доступны
только шагу подписанной сборки при ручном запуске доверенного `master`. Keystore временно
записывается в `RUNNER_TEMP` с закрытыми правами и удаляется после шага. Нельзя создавать
новый ключ для каждого запуска или подменять публичный отпечаток ради прохождения проверки.

Для Linux с уже подготовленными переменными `ZHUZHALKA_KEYSTORE_PATH` (абсолютный путь)
и `ZHUZHALKA_KEYSTORE_PASSWORD`:

```bash
ANDROID_BUILD_TYPE=release bash scripts/build-android.sh
python3 scripts/package-release.py --output release-dist
```

Облачная сборка не равнозначна отдельному тесту её APK в эмуляторе.
